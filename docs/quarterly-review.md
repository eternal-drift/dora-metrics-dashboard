# Sample Quarterly Engineering Review

A worked example of the artifact this system exists to make possible: a
quarterly review built from queryable data rather than assembled by hand
from Slack threads and memory. Based on the seeded demo dataset
(`acme/widgets`, 26-week window) — see [before-after-intervention.md](before-after-intervention.md)
for the underlying numbers and their caveats.

---

## Q2 Engineering Review — Platform Team (acme/widgets)

### Summary

Delivery speed and release stability both improved this quarter without
trade-off — PR cycle time down 55%, change failure rate down from ~35% to
~5%, throughput up 52%. The improvement is consistent with tighter PR
scoping and faster review turnaround rather than a one-time push, based on
the smoothness of the trend across the window (see caveat below).

### What moved, and why we believe it

| Metric | Q start | Q end | Likely driver |
|---|---|---|---|
| PR cycle time | 43.9h | 19.7h | Smaller PRs, faster first-review turnaround |
| Change failure rate | ~35% | ~5% | Release hygiene, better pre-release testing |
| Throughput | 23/mo | 35/mo | More reviewers unblocked sooner (downstream of cycle time) |
| PR volume | 3–6/wk | 7–10/wk | Smaller PRs land more often at similar total scope |

### What we're watching next quarter

- **WIP per engineer** is currently healthy (~1–2), but throughput growth
  without a corresponding WIP check can mask individuals quietly
  overcommitting — see the scorecard's per-metric status rule in
  [engineering-health-scorecard.md](engineering-health-scorecard.md).
- **MTTR** has no incident data this period. That's either genuinely good
  news or a sign incident-tracking discipline has lapsed — needs a manual
  check, not something this system can distinguish on its own (see
  [metrics.md](metrics.md) MTTR caveat).
- **Lead time for changes** depends on release batching cadence; if
  releases get less frequent next quarter this number will look worse even
  if nothing about engineering speed changed — a known proxy caveat, not a
  new problem.

### Risks and caveats disclosed with this review

- Change failure rate is a keyword-heuristic proxy (hotfix/revert/rollback
  merges within 24h of a release), not a direct incident count — see
  [metrics.md](metrics.md). A team that stopped labeling hotfixes as such
  would show a false improvement here.
- This review is a **sample built on synthetic seeded data** to
  demonstrate the reporting format this system produces — see
  [ADR 0003](adr/0003-synthetic-jira-instead-of-live-integration.md). A
  real quarterly review generated by this system would carry the same
  structure against real ingested data.

### Ask

No headcount or process changes requested this quarter — current trend is
healthy. Recommend revisiting the WIP-per-engineer threshold if throughput
growth continues at this rate into next quarter, per the "what we're
watching" note above.
